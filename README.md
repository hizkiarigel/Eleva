# Eleva — Web MVP (Beta)

AI Character Growth System. Alur: Daftar (kode beta) → Onboarding → AI Analysis → Daily Quest → Reflection → Dashboard.

Beta gratis, pilot tertutup 10 orang terundang selama 14 hari lewat kode undangan (`BETA_CODE`) — bukan pendaftaran terbuka. Postgres (multi-user), Express backend, vanilla JS frontend. Tanpa build step. Model AI: Claude Sonnet (bukan Haiku — kualitas "mentor voice" adalah validasi utama pilot ini, biayanya jauh di bawah budget di skala 10 orang).

**Belum ada pembayaran/billing** — beta ini gratis sampai periode betanya selesai. Jangan diasumsikan ada monetisasi aktif.

## Jalanin di lokal

Butuh Postgres lokal (`createdb eleva_dev` atau setara).

```bash
npm install
cp .env.example .env
# isi ANTHROPIC_API_KEY, DATABASE_URL, BETA_CODE, SESSION_SECRET di .env — lihat komentar di .env.example
npm start
```

Buka `http://localhost:3000`. Tanpa akun, kamu akan diarahkan ke layar daftar/masuk — daftar butuh `BETA_CODE` yang cocok dengan env var-nya.

Tanpa `ANTHROPIC_API_KEY`, aplikasi tetap jalan — quest jadi generik (fallback), dan refleksi tidak menaikkan stat. Ini disengaja: tidak ada AI mentor sungguhan, tidak ada growth palsu.

## Struktur

```
server/
  index.js    → Express app + routes, semua route app di belakang auth middleware
  auth.js     → signup/login (bcrypt + BETA_CODE), dipanggil dari index.js
  db.js       → Postgres (pg), semua query di-scope per user_id
  claude.js   → panggilan ke Claude API + fallback kalau key belum ada / gagal
  safety.js   → deteksi frasa krisis, independen dari AI (lihat bagian Prinsip di bawah)
public/
  index.html, styles.css, app.js  → frontend vanilla JS, termasuk layar auth + privacy notice
reference/
  Eleva_Prototype.jsx              → prototype React yang jadi acuan fitur Pathway (bukan bagian dari app produksi)
  Eleva_Correlation_Matrix.html    → peta bukti riset 21 pasangan sinergi radar (buka di browser, tap sel untuk sitasi)
  ELEVA_Constitution_Product_Bible_v1.9.docx → filosofi produk & changelog keputusan (v1.5 = 7 elemen MECE; v1.6-v1.7 = rename+reframe Pathway; v1.8 = gate kespesifikan; v1.9 = input terstruktur quest fisik + roadmap Capacitor; menggantikan v1.7 yang di-commit sebelumnya)
```

## Auth & multi-tenant

- Email + password (di-hash pakai bcrypt), session lewat cookie httpOnly yang di-sign (`cookie-session`, secret dari `SESSION_SECRET`). Tidak ada magic link/OAuth, tidak ada flow lupa password — sengaja sederhana untuk beta terkontrol.
- Signup wajib isi `BETA_CODE` yang cocok dengan env var — cara paling sederhana buat batasi kecepatan pertumbuhan (dan biaya API) selama beta.
- Semua route data (`/api/state`, `/api/profile`, `/api/reflection`, `/api/reset`) ada di belakang middleware auth dan **selalu discope dari `req.userId` (session), bukan dari body/param request** — supaya user tidak bisa akses/ubah data user lain walau coba manipulasi request API langsung.
- Privacy notice singkat (bukan kebijakan privasi hukum formal) ditampilkan di layar daftar, wajib dicentang sebelum tombol daftar aktif.

## Prinsip desain yang tertanam di kode (bukan cuma di dokumen)

- **Growth butuh substansi — tiga lapis anti-Goodhart** (Bible bab 11): (1) gate deterministik `wordCount` di `server/index.js` — refleksi di bawah ~12 kata tidak pernah menaikkan stat; (2) **gate kespesifikan** (sejak v15/Bible v1.8, di prompt `processReflection`): kalau deskripsi quest eksplisit meminta detail konkret (angka/ukuran/observasi), refleksi generik yang tidak menyebut satu pun detail itu ditolak growth-nya BERAPA PUN panjangnya — refleksi singkat-tapi-spesifik justru sah, dan quest kualitatif yang tidak minta angka tidak dipaksakan standar angka; (3) **input terstruktur untuk quest fisik** (sejak v15/Bible v1.9): quest cardio/gym diselesaikan lewat field angka (jenis/durasi/jarak/RPE/titik berat, atau gerakan/set×rep/beban) yang kelengkapan & kewajarannya divalidasi kode (`server/structured.js` — kombinasi mustahil seperti "lari 15 km dalam 20 menit" ditolak dengan pesan jelas), refleksi naratif jadi opsional, dan angkanya jadi baseline progresif untuk quest berikutnya ("minggu lalu 15 repetisi, sekarang coba 18").
- **Riwayat jujur soal hari yang terlewat** (bug dilaporkan founder di produksi, 10 Agustus): dashboard sempat menampilkan hari yang TIDAK pernah direfleksikan sebagai entri polos di bawah "RIWAYAT" — bedanya cuma warna border tipis, gampang terbaca sekilas di layar HP seolah sudah tercatat/selesai padahal belum dikerjakan sama sekali. `allHistory` (`server/db.js`) memang sengaja mengembalikan SEMUA hari lampau termasuk yang `reflection`-nya masih null — menyembunyikan hari terlewat dari riwayat justru bentuk lain dari menyamarkan progres, bukan lebih jujur. Perbaikannya di lapisan tampilan (`public/app.js`+`styles.css`): entri tanpa refleksi sekarang dapat class `.missed` (border rust, redup) plus label eksplisit "Terlewat — belum dikerjakan", kontras jelas dari entri selesai (border hijau + cuplikan refleksi asli). Susulan founder di hari yang sama: hari terlewat juga harus tetap terlihat langsung di area QUEST HARI INI, bukan cuma di Riwayat yang perlu discroll — `.quest-carousel` (pola scroll-snap yang sama dengan Pathway carousel v7) menaruh kartu hari ini sebagai slide pertama diikuti kartu-kartu hari terlewat (read-only, tanpa tombol aksi — sengaja tidak membuka jalur refleksi retroaktif, itu keputusan terpisah soal integritas growth-gate, bukan sekadar preferensi tampilan), digeser lewat swipe horizontal; caption kecil di bawah carousel menghitung berapa yang terlewat. Carousel otomatis kembali ke kartu tunggal (tanpa swipe) begitu pengguna mulai mengisi refleksi hari ini, supaya gestur geser horizontal tidak berebut sentuhan dengan mengetik di form.
- **Chapter tidak naik karena waktu/EXP**: hanya naik tiap kelipatan 5 sesi growth yang valid, dan hanya kalau AI menilai ada pergeseran pola nyata.
- **AI mentor, bukan terapis** (`server/claude.js`, system prompt + `server/safety.js`, deteksi server-side): dua lapis. Prompt AI diinstruksikan mengarahkan ke bantuan profesional kalau refleksi menunjukkan tanda krisis. Di atas itu, `POST /api/reflection` juga mengecek `text` terhadap daftar frasa risiko tinggi secara independen dari AI — kalau cocok, AI mentor tidak dipanggil sama sekali dan `mentorReply` diganti kontak Layanan Sejiwa/Healing119 (119 ext. 8 / www.healing119.id), tanpa growth untuk sesi itu. Lihat bab 12 di dokumen bible untuk kenapa ini penting sekarang sudah ada user lain selain founder.

## Onboarding & Pathway (adaptif, v8 — Pathway direname+direframe per Bible v1.7)

Onboarding: **Nama + Privacy Promise** (satu layar, checkbox konfirmasi) → **Radar self-assessment** (**7 sumbu MECE** per Bible v1.5 — Body, Growth (gabungan Mind+Explorer), Livelihood (gabungan Career+Finance), Emotional Stability, Social, Purpose, Autonomy (baru, dari Self-Determination Theory) — drag titik sudut, skala 1-10, default 5, total SELALU tepat 35; redistribusi memakai **re-normalisasi satu pool** (`applySynergyDrag` di `public/app.js`): semua sumbu lain yang belum terkunci berubah total PERSIS −delta, dibagi sebanding "kekuatan tarik" masing-masing — partner ber-evidence riset menurut bobotnya (`SYNERGY`, 14 dari 21 pasangan ber-evidence, sitasi lengkap di `reference/Eleva_Correlation_Matrix.html`; 3 pasangan "campuran" + 4 belum-ketemu ikut menyerap netral proporsional ke nilainya — **sejak v9, skala bobot lemah/sedang/kuat = 2/4/6** (digandakan dari 1/2/3) dan **sejak v10 pull non-partner diredam 0.5× nilai-saat-ini** — dua-duanya supaya partner ber-evidence kuat jelas mengungguli non-partner di chart (drag tunggal sekarang menghasilkan gradien terbaca: partner kuat bergerak paling banyak), sekaligus supaya sumbu yang konsisten dipilih di kartu kalibrasi tidak digerogoti balik oleh sinyal-sinyal berikutnya) — rumus yang sama untuk semua topologi, jadi sumbu paling terhubung sekalipun (Autonomy: 5 partner, cuma Social non-partner murninya) tetap bisa digeser mulus; sumbu yang sudah mentok di floor/ceiling dikecualikan dari pool (bukan memblokir seluruh gesekan — bug yang pernah dilaporkan founder), constraint-solving menskalakan seluruh delta kalau ada titik mau keluar 1-10, pembulatan largest-remainder menjaga total presisi 35, feedback getar+teks saat mentok; angka nilai tampil di tiap titik, dan tap titik = kunci/buka — maksimal 3 titik terkunci yang tidak ikut bergeser numerik, jadi kombinasi ekstrem kayak dua sumbu 10 sekaligus mungkin kalau dua-duanya dikunci; info kunci jadi konteks buat AI, bukan rumus makna tetap di kode) → **Adaptive Scenario Cards** (2-6 kartu: tiap kartu satu skenario + TEPAT 4 opsi, masing-masing mewakili satu sumbu — **sejak v7, sumbu terkunci BOLEH ikut jadi opsi** (dibalik dari v6 yang mengecualikannya), supaya cakupan tetap mencakup SEMUA 7 sumbu, bukan cuma yang unlocked; pengguna WAJIB pilih 1 favorit 👍 DAN 1 dari sisanya paling-tidak-disukai 👎; pemilihan 4 sumbu per kartu diprioritaskan ke yang paling sedikit/belum muncul; berhenti minimal 2 kartu maksimal 6, dua syarat — minimal & cakupan penuh — ditegakkan di kode) → **kalibrasi radar** (tiap kartu menghasilkan 2 sinyal — favorit=+2, paling-tidak-disukai=−2 (**sejak v11**, digandakan dari ±1 atas permintaan founder supaya pola pilihan konsisten terasa lebih cepat "membuktikan diri") — diterapkan lewat mesin redistribusi yang SAMA dengan drag manual; dibatasi ±3 net kumulatif per sumbu unlocked untuk sinyal langsungnya (cap TIDAK berubah, cuma butuh lebih sedikit pilihan konsisten untuk mentok ke situ); **sumbu terkunci kebal dari pilihan yang MENDUKUNG kuncinya, tapi sejak v12 BOLEH terkikis kalau pilihan berulang kali BERLAWANAN** (mis. dikunci tinggi tapi berulang jadi paling-tidak-disukai) — SETIAP pilihan berlawanan (bukan cuma setelah ambang tertentu) langsung menggerakkan angkanya lewat mesin kalibrasi yang sama (±2 per pilihan, cap ±3 total, persis seperti sumbu unlocked), dinilai terhadap nilai SAAT DIKUNCI (bukan nilai yang mungkin sudah bergeser) supaya arahnya tidak terbalik di tengah sesi; sumbu tetap berstatus "terkunci" sepanjang proses (kebal dari geseran sumbu LAIN, tetap ikon 🔒) — cuma sinyal kontradiksi kartu yang bisa menggerakkannya. Chapter Analysis WAJIB menyebut pergeseran ini konkret (before→after) kalau terjadi, dan tetap memunculkan pertanyaan reflektif untuk pola berulang; pergeseran ≥2 poin dari radar mentah pada sumbu unlocked WAJIB disebutkan eksplisit juga — radar mentah (`radar_raw`) dan radar terkalibrasi (`radar_snapshot`) tersimpan terpisah untuk audit) → **Chapter Analysis** (insight naratif AI, **sejak v7 selalu menampilkan visual radar mentah-vs-terkalibrasi bertumpuk** — bukan cuma teks — pakai geometri SVG yang sama dengan radar interaktif tapi read-only) → **Pathway Recommendation, sejak v7 berupa 3 KARTU yang bisa digeser** (carousel horizontal): Kartu 1 = pathway terkalibrasi (rekomendasi AI penuh-konteks, seperti sebelumnya), Kartu 2 = pathway dari radar MENTAH saja (AI diminta abaikan seluruh jawaban kartu skenario untuk kandidat ini, diminta di panggilan API yang sama demi efisiensi), Kartu 3 = wildcard acak client-side (bukan analisis AI) — ketiganya dijamin pathway berbeda-beda (dedup dengan fallback ke kandidat berikutnya), user WAJIB tap salah satu sebelum tombol konfirmasi aktif (tidak ada default) — plus Secondary Trait opsional, informasional saja → konfirmasi pathway dari kartu yang dipilih ATAU override manual lewat teks bebas ("Bukan ini — aku tahu persis mau melatih apa") → **Goal capture (v13, jembatan ke First Trial — bukan step onboarding):** setelah Pathway dikonfirmasi, sebelum quest hari pertama, layar *"Apa yang mau kamu capai selama masa ini?"* menerima **1-3 goal free-text** (area beda-beda sekaligus itu wajar, mis. kesehatan + bahasa + karier). Placeholder-nya **per-Pathway (v14)** — Architect/Warden/Weaver/Pilgrim dapat contoh statis sesuai gayanya masing-masing, Specialist dapat placeholder dinamis dari domain custom yang sudah diisi user (fix dari bug v13: placeholder sempat jadi contoh pribadi founder secara literal untuk semua orang). Prinsip inti: **Goal menentukan APA, Pathway menentukan BAGAIMANA** — Pathway konstan sepanjang First Trial, quest harian menggarap SATU goal per hari lewat rotasi deterministik di kode (goal paling lama belum disentuh dapat giliran — prinsip cakupan yang sama dengan kartu skenario; `quest.goalIndex` distempel server, bukan dipercaya dari AI), dan gaya Pathway wajib konsisten lintas goal (IELTS ala Pilgrim = "coba 3 metode belajar dulu", ala Architect = "susun jadwal terstruktur" — goal sama, pendekatan beda). Radar boleh dominan di area berbeda dari goal — itu bukan kontradiksi: radar = kondisi, goal = target, Pathway = gaya. **Sejak v14**, Quest yang menyasar goal dirancang lewat kerangka **WOOP** (Wish-Outcome-Obstacle-Plan) secara implisit di prompt AI — bukan kolom input baru — AI memikirkan hambatan spesifik yang mungkin bikin goal itu gagal buat orang ini (dari radar+profil), lalu instruksinya dirancang mengantisipasi itu, tanpa pernah menulis "Obstacle:/Plan:" eksplisit ke pengguna.

**Icon bantuan kontekstual (v15):** kelima layar inti (radar, kartu skenario, carousel Pathway, goal capture, dashboard) punya icon "?" konsisten di pojok kanan atas — tap untuk sheet ringan berisi penjelasan layar itu saja dalam bahasa awam (teks statis per layar, bukan AI-generated), tutup lewat tombol atau tap area gelap.

Radar chart menggantikan dua mekanisme terpisah dari desain sebelumnya (Stats polygon + Growth Focus multi-select) — bentuknya sendiri (sumbu mana yang menonjol/ditekan) jadi sinyal minat pengguna, sekaligus nilai awal untuk `stats` (dikonversi ×10 ke skala 0-100 yang di-grow refleksi harian).

**Sejak v8, lima Pathway** (turun dari enam, Explorer dihapus di Bible v1.6 karena wilayahnya sudah tercakup stat Growth): **Architect** (membangun & menyusun metodis), **Warden** (menjaga & mempertahankan, fondasi konsisten), **Weaver** (menghubungkan orang & ide), **Pilgrim** (menjelajah luas sengaja sebelum berkomitmen), **Specialist** (menyelam dalam satu domain spesifik, pengguna menulis sendiri spesialisasinya). Bible v1.7 mengganti nama DAN makna sekaligus (Builder/Guardian/Connector/Seeker lama → Architect/Warden/Weaver/Pilgrim) untuk menegakkan prinsip **Pathway ≠ Chapter**: Chapter menjawab "lagi di fase/masalah hidup apa" (temporal, berubah — mis. "Lost"→"Healing"), Pathway menjawab "bagaimana gaya orang ini berinteraksi dengan dunia" (tahan lama, soal gaya perilaku, BUKAN masalah yang sedang dihadapi). Aturan ini ditegakkan eksplisit di system prompt AI (dengan contoh benar/salah), berlaku untuk semua teks yang menyebut Pathway — bukan cuma di Chapter Analysis. Akun lama dengan pathway lama (mis. "Builder") tetap tampil apa adanya, bukan error — bukan bagian dari data migrasi, sama seperti pola radar 7-sumbu sebelumnya.

Pathway baru (dari kartu mana pun yang dipilih, atau override) mulai berstatus **trial** (`pathway_status`), bukan langsung permanen. Growth-gate 12-kata tetap berlaku penuh selama trial. Setelah ≥14 hari **dan** ≥5 growth session asli, resonance-check (dievaluasi lazy tiap `GET /api/state`) otomatis mengaktifkannya permanen; kalau belum cukup data, trial diperpanjang — tidak ada skor AI tersembunyi, semuanya traceable ke data refleksi nyata. AI menurunkan `pathwayNoun` (satu kata benda peran, mis. "Closer" untuk pathway "Sales") sekali dan mempertahankannya persis sama setiap hari setelahnya — ditampilkan sebagai badge `{tier} {pathwayNoun}` di dashboard (`tier` dari `growthSessions` pembagi 3, beda dari kenaikan chapter yang pembagi 5), dengan penanda tambahan `(hipotesis — First Trial)` selama masih trial. AI juga memilih tiap hari apakah instruksinya berbentuk "Quest" (aksi konkret) atau "Acting Method" (praktik cara bersikap) berdasarkan Pathway & chapter — dua framing ini tidak pernah muncul bersamaan.

Akun yang onboarding sebelum radar chart ada (masih punya `growth_focus` + Situasi/Values/Fear di data lama mereka, belum punya `radar_snapshot`) tetap dapat quest harian yang personal — context AI jatuh balik ke field lama mereka kalau field baru belum ada, jadi tidak ada yang mendadak kehilangan "kompas"-nya gara-gara redesign ini.

Akun era radar 8-sumbu (pre-MECE) juga TIDAK dimigrasikan otomatis — keputusan sadar dari PRD: belum ada beta member asli, cuma data testing founder, jadi migrasi 8→7 sekali-pakai lebih mahal daripada reset. Dashboard tetap menampilkan stats lama mereka apa adanya (label legacy Mind/Career/Finance/Explorer), AI tetap membaca snapshot lama sebagai konteks, dan jalur resminya: tombol **↺ Reset data** di dashboard → onboarding ulang dengan 7 elemen baru.

Keterbatasan yang jujur dicatat: resonance-check 14-hari cuma diverifikasi lewat simulasi tanggal (`pathway_trial_started_at` dimundurkan manual di Postgres saat testing), belum lewat pengguna asli yang benar-benar menunggu 14 hari kalender.

## Prompt caching

`server/claude.js`'s system prompt (`MENTOR_SYSTEM`, sama persis di setiap panggilan onboarding maupun harian) pakai `cache_control` Anthropic supaya panggilan berulang dalam window cache lebih murah. Catatan jujur: system prompt saat ini diperkirakan masih di bawah ambang minimum 1024 token yang dibutuhkan model (`claude-sonnet-4-6`) supaya benar-benar ke-cache — kodenya sudah terpasang (tidak ada biaya tambahan kalau belum ke-cache), tapi cache hit belum terverifikasi jalan nyata. Cek `cache_read_input_tokens` di log (`[claude usage] ...`) begitu jalan di production dengan API key aktif.

## Deployment

Butuh Postgres (bukan lagi SQLite) + proses Node.js yang hidup terus. Panduan konkret:

- `DEPLOY_RAILWAY.md` — deploy dari GitHub repo, tambah Postgres service di project yang sama (`DATABASE_URL` otomatis ter-link).
- `DEPLOY_HOSTINGER.md` — kalau mau tetap di domain sendiri (subdomain di Hostinger Business/Cloud).

Sebelum benar-benar membagikan kode beta ke siapa pun: verifikasi 2 akun test terpisah, pastikan datanya tidak bocor lintas user sama sekali (termasuk lewat manipulasi request API langsung, bukan cuma lewat UI).
